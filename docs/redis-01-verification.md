## API와 초기 용량

```java
import miniredis.store.KeyValueStore;

// 100,000은 사용 예시다. 호출자가 실제 예상 최대 고유 키 수를 지정한다.
var store = new KeyValueStore(100_000);
store.put("product:1", "사과");
store.get("product:1");    // Optional.of("사과")
store.put("product:1", "");
store.get("product:1");    // Optional.of("") — 존재하는 빈 값
store.get("missing");      // Optional.empty() — 없는 키
store.delete("product:1"); // true, 이미 없는 키는 false
store.size();              // 0
```

- `KeyValueStore`는 저장소 진입점이고, package-private `StringHashTable`이 실제 배열과 체인을 관리한다. `HashMap`이나 기존 맵으로 저장을 위임하지 않는다.
- 예상 키 수 `N`을 받아 `max(1, ceil(4N / 3))`개 버킷을 만든다. `N = 100000`이면 133334개이며, 그 수까지 신규 키를 넣어도 확장하지 않는 것을 테스트한다. 이는 성능 측정 결과가 아니라 용량 정책 검증이다.
- 기본 크기 16이나 데이터 크기 10만을 하드코딩하지 않는다. 예상 수가 0이면 버킷 1개로 시작해 필요에 따라 확장한다. 예상 수는 저장 가능한 키 개수의 상한이 아니다.
- 키/값은 문자열이며 빈 문자열을 허용한다. `null` 키·값과 음수 예상 수는 `IllegalArgumentException`으로 거절한다. 예상 수 계산은 long으로 수행하고 int 배열 길이로 표현할 수 없으면 할당 전에 거절한다. 표현 가능한 용량도 실제 힙이 부족하면 할당에 실패할 수 있다.
- `size()`는 서로 다른 키 개수다. 내부 테스트용 용량 조회는 package-private이며 외부 저장소 API에는 노출하지 않는다.

## 자료구조와 함수 흐름

1. **버킷 선택:** `Math.floorMod(key.hashCode(), capacity)`로 계산한다. 음수 해시와 `Integer.MIN_VALUE`도 유효한 인덱스로 처리하며 임의의 양수 용량을 지원한다.
2. **충돌:** 각 배열 원소는 `key`, `value`, `next` 노드로 된 단방향 체인이다. 노드를 순회하며 `String.equals`로 키 내용을 비교한다. 해시나 객체 주소가 같다는 이유만으로 같은 키로 취급하지 않는다.
3. **저장·덮어쓰기:** 먼저 기존 키를 찾는다. 있으면 값만 바꾸고 종료한다. 없으면 확장 여부를 판단한 뒤 체인 앞에 노드를 추가하고 크기를 한 번만 증가시킨다.
4. **조회:** 선택한 체인에서 키를 찾으면 `Optional.of(value)`, 끝까지 없으면 `Optional.empty()`를 반환한다. null 값을 허용하지 않아 빈 값과 미스가 섞이지 않는다.
5. **삭제:** 이전 노드와 현재 노드를 추적한다. 머리 삭제는 버킷의 시작 노드를, 중간·꼬리 삭제는 이전 노드의 next를 갱신한다. 실제 삭제에만 크기를 줄인다.
6. **확장:** 신규 삽입 후 예상 적재율이 0.75를 초과하는지 `(size + 1L) * 4 > capacity * 3L`로 검사한다. 버킷 수를 정확히 두 배로 늘리고 모든 노드의 인덱스를 재계산한다. 노드를 재사용하며 다음 노드를 먼저 보존해 체인을 잃지 않고, 재배치 중 size는 바꾸지 않는다. 두 배 용량이 int 범위를 벗어나면 확장 전에 실패한다.

예를 들어 용량 4에서 키 3개는 적재율 0.75이므로 유지한다. 같은 키를 덮어써도 유지하며, 네 번째 고유 키를 저장할 때 용량을 8로 확장한다. 체이닝에서는 키가 한 버킷에 몰리더라도 적재율은 전체 키 수/전체 버킷 수로 계산한다.

## 검증과 재현

Java 25 JDK를 선택한 환경에서 다음 명령을 실행한다.

```sh
cd mini-redis
./mvnw test
```

2026-11-13, 기준 커밋 `881be2c` 위 **미커밋 작업 트리**에서 Temurin 25.0.5와 Maven 3.9.11로 확인했다. 시스템 기본 JDK는 17이므로 검증 시 임시 디렉터리의 기존 JDK 25와 Maven 캐시를 환경 변수로 지정했다. 빌드 도구의 Guice Unsafe 경고는 기존 0단계와 동일하다.

| 항목 | 확인 내용 |
|---|---|
| 기본 동작 | 저장·조회, 내용이 같은 별도 String 객체의 덮어쓰기, 삭제·반복 삭제, 없는 키 삭제 시 기존 값 유지 |
| 빈 값·입력 검증 | 빈 문자열 키·값, 미스와의 구분, null 거절 시 값·크기·용량 불변 |
| 충돌 | 동일 해시 키와 다른 해시지만 같은 버킷인 키를 구분, 체인의 머리·중간·꼬리 삭제, 같은 해시의 미등록 키 조회·삭제 |
| 경계 | 용량 4에서 키 3개 유지, 덮어쓰기 유지, 네 번째 키에서 8로 확장. 다음 경계인 키 6개/7개에서도 검증 |
| 재배치 | 용량 변경 시 인덱스가 실제 바뀌는 기존 키, 충돌 체인, 1000개 삽입 후 반복 확장·덮어쓰기·전체 삭제 |

| 정수 경계 | Integer.MIN_VALUE 해시, 음수·표현 불가능한 예상 크기, 잘못된 초기 용량 |

테스트를 먼저 추가했을 때는 구현 클래스가 없어 컴파일 실패하는 것을 확인했다. 구현 후 JUnit 결과는 **33개 실행, 실패 0, 오류 0, 생략 0**이다. 실행 시간은 성능 비교 수치로 사용하지 않는다.

추가로 두 운영 소스 파일을 JDK 25의 `javac --release 25 -Xlint:all -Werror`로 별도 컴파일해 경고 없이 통과했다. 프로젝트 문서 7개의 상대 링크·앵커 29개, 요구사항 ID 10개와 연결표, `git diff --check`도 통과했다. 운영 코드가 기존 Map 구현을 사용하지 않는 것을 확인했다.

## 남은 제약

- 단일 스레드용 메모리 자료구조다. 종료 시 데이터는 사라지고 동시 요청·만료 처리는 지원하지 않는다.
- 리사이즈 중 전체 행을 재배치하며 삭제 시 버킷 배열을 축소하지 않는다. 키 분포가 편향되면 체인이 길어질 수 있고, 동일 해시 키는 버킷을 늘려도 분산되지 않는다.
- 사전 할당으로 예상 수까지 확장을 피하는 것은 검증했지만, 처리량·지연·힙/GC 비교는 수행하지 않았다. 최적 성능이나 개선 배수를 주장하지 않는다.
- 별도 lint/정적 분석 도구는 미설정이며 이번에 추가하지 않았다. 위 JDK 컴파일러 경고 검사와 문서/차이 검사로 확인한 범위만 통과로 보고한다.
- 커밋·Push·PR 생성·Jira 완료 전환은 수행하지 않는다. 완료 전환은 팀 규칙의 통합 조건을 따른다.
